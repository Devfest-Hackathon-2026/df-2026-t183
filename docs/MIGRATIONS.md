# データのマイグレーション

## 初回リリース

第1段階は Firestore を使わないため、移行はない。以下は第2段階で保存を入れるときの準備。

1. 検証環境と審査環境の Firestore を分ける。Go の実行用サービスアカウントに必要な権限だけを付け、ブラウザ SDK から直接読み書きできないことを確認する。
2. [データ設計](DATABASE_DESIGN.md) の `learningSessions` と `viewKeys` に `expiresAt` の TTL ポリシーを設定する。公開前に有効化を確認する。
3. `learningSessions` は ID で取得する。本文・履歴・振り返り・ダイジェストは単一フィールドの索引から除外する。`viewKeys` もドキュメント ID で取得し、検索しない。検索や並び替えのためのインデックスを追加する場合は、必要性と読むデータを記録する。
4. 検証環境で、期限切れを API が即時拒否することと、TTL が後からレコードを削除することを別々に確認する。削除印と `viewKeys` にも TTL を使う。
5. IAM、ルール、TTL、インデックスの設定と適用結果を記録する。GitHub への push だけでは適用されない。

## リポジトリに含む設定

- `firestore.rules` はブラウザなどのクライアント SDK の読み書きをすべて拒否する。Go のサーバー SDK は IAM で認可されるため、このルールだけではサーバーの権限を制限できない。
- `firestore.indexes.json` は本文・履歴・振り返り・ダイジェストの単一フィールド索引を除外し、両コレクションの `expiresAt` を TTL 対象にする。TTL と索引除外は既存データにも影響するため、対象プロジェクトを確認して適用する。
- `firebase.json` から上の2ファイルを参照する。ファイルをコミットしただけではクラウドに適用されない。この変更のローカル検証ではデプロイを行わない。
- 公開前に、対象環境の既存ルール・索引を確認し、承認された環境でのみ `firebase deploy --project "$RUN_PROJECT" --only firestore` を実行する。コレクションを他アプリと共有している場合は、既存設定への影響を先に確認する。TTL ポリシーが有効になるまで待ち、API の即時失効とは分けて検証する。

## 形式を変える場合

- 先に旧形式と新形式の両方を読める実装を出し、その後で `schemaVersion` を上げて新形式を書き込む。保存済みの閲覧キーで旧記録を開けることを確認する。
- 移行は再実行できるようにし、期限切れや削除済みのデータを復活させない。`savedAt`、`expiresAt`、`viewKeyId` を理由なく変更しない。
- 既存記録の TTL 延長や新しいデータの保存は、利用者への案内と合わせて決める。確認用の一括初期化は検証環境に限る。

## 差し戻し

Cloud Run と Web を戻す前に、旧リビジョンで新旧レコードと発行済みのキーを扱えるか確認する。互換性がなければ読み込みを壊す旧版に戻さず、修正版を出す。TTL と削除印は維持する。
